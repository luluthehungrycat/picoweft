# PicoWeft product specification

## Purpose

PicoWeft is a general-purpose autonomous agent harness for small, locally runnable language models. It helps those models complete as broad and deep a range of tasks as they can reliably handle within real context, RAM, compute, thermal and power budgets. A task can span multiple model and tool turns, produce an independently checkable result and survive interruptions. The user supplies the objective and authorizes capabilities. The harness owns execution, budgets, state and verification.

The first product is a self-contained Android app. The second is a general Linux CLI, with a TUI only when it improves actual workflows. Phones, tablets, SBCs and low-resource laptops are valid targets. Design one portable core and use a Linux fixture early to make Android development testable. Android remains the first user-facing target. iOS, other platforms and hardware acceleration beyond the proven CPU baseline are future possibilities.

## Product and lineage decisions

- This is a fresh MIT-licensed project. Edgmes Agent is a historical reference. Its capability, routing and ledger behavior and tests may be adapted selectively; its single-response Ollama runtime is not the foundation for the new loop. Keep provenance and the applicable license and notices with any copied or adapted material.
- Study Pi Agent for a small loop, explicit model and tool seams, observable events and session reconstruction. Study Hermes Agent for useful skills, memory and profile behavior. Maintain explicit dependency pins and relevant upstream security updates. Neither upstream tree is a merge target or a runtime dependency by default.
- Compatibility means individually documented and tested formats, providers or features. Selected Markdown skills, profile settings or transcript interchange may be worth supporting. Importing a format does not imply compatibility with executable extensions, shell helpers, credentials, sessions or all tool semantics.
- Use an MIT license for PicoWeft-owned work and audit third-party code, binaries, and model artifacts separately. Record source revisions and notices. A model's download or redistribution terms are independent of the repository license.

## Required topology and provisional technology

One Rust core owns the loop, task and session semantics, context projection, policy, validation, budgets and event contracts. A Kotlin Android host owns UI, lifecycle, OS permissions, platform tools, storage integration and credentials. A Linux CLI host uses the same Rust core and supplies Linux equivalents. Keep a library boundary suitable for future hosts without shipping speculative SDKs. Start with a simple Cargo workspace and an Android app module grouped by responsibility. Choose exact paths, dependencies, minimum Android API and UI toolkit after checking the target phone and the native dependency build; document choices and verified support.

Start with a pinned upstream llama.cpp ARM64 CPU backend. Keep native backend selection and model formatting behind adapters. Use a small typed in-process core contract. Treat OpenAI-compatible HTTP as one adapter for remote/private endpoints or Linux experiments. Android local inference must work inside the app installation without Termux, an external daemon, an open listener or a separate server. A private service process for isolation can be evaluated later if measured lifecycle or crash behavior warrants it.

First validate a narrow Rust Android integration path against a fake provider and one host-tool result. Pass events in bounded batches across JNI, use explicit handle ownership, keep native work off the UI thread, propagate stop requests to inference, and verify cleanup and app-owned persistence. Test the required GGUF tokenizer, chat template, grammar or native tool-call controls in the pinned binding; prefer a narrow shim over an inference fork if the binding needs extension. Rust stays provisional until this probe is tested. A shared Kotlin/JVM core is the fallback if sustained ABI, packaging, cancellation or maintenance costs outweigh Rust's Linux advantages. Record evidence before switching. Avoid two production loops and avoid building two full prototypes to decide.

## Core execution contract

### Sessions, turns and restart

Give sessions, turns and tool calls stable IDs. One active execution per session is sufficient initially. Commit user input, accepted assistant messages, tool intent, outcome and checkpoints to app-owned durable storage at defined points. Expose ordered, versioned lifecycle events for generation, completed calls, tool execution, cancellation and terminal outcome. Streaming deltas are display data until validated and committed. Consumers may reconnect and reconstruct from durable state. Keep session storage separate from the input projected into the model.

After process death mark interrupted work explicitly. Persist tool intent before a side-effecting action and its result after execution. If a crash leaves the outcome uncertain, surface that state and reconcile through the tool or ask the user before trying again. Never automatically replay an ambiguous mutation. A read-only tool may be retried only under explicit retry policy, within budget. Use stable idempotency keys where host tools support them. Resume from a durable checkpoint without silently changing profiles or sending data off-device. Use atomic writes or transactions and schema versions. Pick a simple local store that meets these invariants. Cross-device session sync is deferred.

### Models and adapters

An adapter supplies model identity, supported modalities and tool/streaming features, effective context and counting behavior, plus a cancellable generation operation. Emit incremental text and tool-call fragments as available, complete calls with stable IDs, completion reason, and usage when available. Normalize errors, refusal, truncation and cancellation. Handle terminal events deterministically. Keep model-specific formatting, constrained decoding and provider streaming semantics in the adapter. Never dispatch partially received, cancelled or truncated tool calls. Supported local and remote modes share the same session and dispatch loop.

A model catalog entry declares tested engine revision, artifact format, quantization, chat template, modality, effective device context and known limitations. Start with a curated LFM3-1.7B Q4 GGUF candidate and a compatible pinned engine. Verify exact artifacts and licenses before including them. Allow a second candidate only where it helps distinguish harness and model behavior. LFM3-VL-2B with a compatible projector is a later goal. Vulkan, vendor GPU backends and NPUs are optional and device/model/driver-specific. Benchmark from an installed APK or actual Linux build before advertising support; a desktop or ADB result alone is insufficient for Android. Fall back visibly to CPU where supported.

### Tools, permissions and autonomy

Tools register a stable name, argument schema, capability requirement, effect classification, timeout and input/output bounds. The core assembles a complete call, rejects unknown names, malformed arguments, duplicate calls and out-of-policy actions, and invokes the authorized host tool. Hosts enforce capabilities again at the OS boundary and return structured outcomes. Model output, documents, tool output, retrieved memory and skills are untrusted data. They cannot expand permissions, authorize tools or override policy. Keep tool exposure separate from execution authorization.

The first app tool is read_saved_note(id) over an app-owned fixture, with bounded output and no path argument or device-wide permission. The Linux test fixture uses an equivalent workspace-scoped capability. Later expand deliberately into app-owned documents, explicitly granted files and content, and other user-approved tools. Consider scoped, observable Linux workspace operations as separate capabilities. Keep ambient filesystem, shell, arbitrary process launch, executable plugins and background autonomy out of the first slice. Permissions, task budgets and OS lifecycle constraints remain host-enforced as capabilities expand. Autonomy means completing multi-step tasks within those bounds, with visible outcomes and a way to stop. Limits on the prototype's tools and steps are evaluation conditions, not permanent product limits.

### Context and resource budgets

Use the actual rendered local chat template and selected tokenizer to calculate context usage. Include fixed instructions, pinned task and constraints, selected history, tool schemas and results, output reservation and margin. Keep a device-tested effective context limit distinct from a model's advertised maximum. For remote providers use supported counters or a conservative documented estimate and server feedback. Do not impose a local or 64k global cap on remote profiles. Bound individual tool results and overall context, tokens, iterations, elapsed time and retry count. Provide explicit cancellation from both hosts. Set initial profile defaults conservatively, expose supported overrides and measure their impact.

Keep current objectives, constraints and essential evidence pinned; reduce optional retrieval before losing necessary state. If compression is added, retain source provenance and test for lost constraints. If mandatory content will not fit, stop visibly and allow a smaller scope or explicitly approved handoff. Avoid clever routing, elaborate planning, automatic memory or model cascades before a simple baseline works. Consider deterministic tool filtering, structured task state or FunctionGemma routing only when task-based comparisons support them. A router cannot grant capabilities or consent.

### Remote inference and privacy

Local mode must not send prompts, notes, tool results or task metadata to a network service. Local inference has no network dependency and makes no silent remote calls for titles, routing, summarization, telemetry, retries or escalation. Model download and an explicitly authorized network tool are separate capabilities.

Provide explicit remote profiles, beginning with one real supported provider/custom endpoint. Retain the goal of larger remote models, including 64k+ where supported, and add relevant provider protocols and Hermes profile interoperability incrementally. Publish a compatibility matrix as support lands. API transport, streaming tool calls and native or subscription authentication must each be verified; importing config does not make desktop credential helpers or arbitrary OAuth flows portable. Never execute imported key commands. Prefer HTTPS for remote profiles; do not forward credentials across untrusted redirects. Treat local/private HTTP endpoints as a distinct explicit configuration. Keep secrets out of the shared transcript, preferences exports, logs and backups. Use host-backed secret storage, including Android Keystore-backed protection for credentials where applicable.

For a local-to-remote handoff, display the destination, model and exact task state proposed for transfer, allow edits or cancellation, and require affirmative consent before sending. An explicitly selected remote turn should visibly identify its profile and data scope. No automatic remote fallback. Network tools have their own permission separate from remote inference. Use offline traffic checks and local mocks as part of verification.

## Android and Linux experience

Android MVP: installable full-stack app with a clear thread view, streaming output, visible model/profile status, stop and interrupted-turn feedback, tool activity and persistent sessions. Use app-private storage and the normal Android permission and lifecycle model. A foreground interactive session is sufficient for the first milestone. Handle configuration changes and test process death. Background work is a later design with OS-compliant lifecycle behavior, not a promise of uninterrupted execution.

The Android MVP includes curated in-app model downloads. A sideload or manually registered fixture may unblock the first technical proof. A trusted app-pinned or authenticated catalog supplies immutable revision, verified artifact sizes/checksums, licenses/notices, supported engine and optional projector. Show storage and network requirements, support progress and cancel, stage privately, check integrity before atomically making an artifact selectable, and recover safely from interruption, full storage or a mismatched download. Support resumability where the server and immutable artifact identity allow it. Keep partial artifacts out of normal model selection.

Linux MVP: CLI for model/profile selection, running and stopping a turn, examining task/tool events and restoring sessions. CPU local inference is baseline. Aim at Linux arm64 and x86-64, documenting what is built and actually tested. The CLI may connect to a separately configured local server for comparison without becoming the only local path. A TUI follows evidence that the CLI workflow needs it. No hardware purchase is a prerequisite.

## Proofs, sequencing and acceptance

1. **Feasibility.** Build a Linux fixture with a fake model to drive the shared loop, then use a small live-model experiment to test bounded task completion. Test native tool calls versus a compact constrained action format where useful. In parallel prove the Android bridge against fake inference, including events, tool result, cancel and cleanup. On Linux use available hardware; fast runs can use a development machine before checking the Pi 400.
2. **Android offline proof.** On a real ARM64 phone, preferably the owner's Nord 2, load a pinned text GGUF and go offline. A user asks about an app-owned note, the model requests the tool, the core validates it, the Kotlin host executes it and the answer uses the returned fact. Capture structured evidence. Restart and inspect the session. Invalid/truncated calls must never execute. Confirm rendering, cancellation and no local-mode traffic. Verify that Linux uses the same shared loop.
3. **Remote proof.** With explicit authorization for live calls and credentials, exercise one real remote/custom profile through the same loop with visible transfer scope, streamed tool calls, cancellation and error handling. Keep mock tests deterministic and report separately when real provider access is unavailable.
4. **MVP delivery.** Add curated downloads, reproducible Android/Linux build guidance, documented target/device matrix, dependency and model provenance, and stable basic CLI/app workflows. Debug builds and emulator runs help development; report physical-device and release packaging evidence separately. Use existing devices. Pi 5, an NPU addon and future GPU devices are unvalidated targets.
5. **Depth evaluation.** Use held-out tasks with expected outcomes, such as selecting among distractors, abstaining from unavailable actions, using tool evidence, recovering from an error, and completing several required steps with a verifiable final artifact in a scoped workspace. Include adverse context pressure, cancellation and interrupted tool execution. Compare changes to the same model, quantization, tools and tasks under a simple loop. Track task success, false actions, time to first token, generation speed, total task time/tokens, peak RAM, cancellation latency and thermal behavior when relevant. State tolerances and protocol before outcomes, record versions, device and repeat counts. No universal benchmark thresholds are assumed. A poor result narrows the next experiment rather than permanently capping autonomy.

Treat a working fake as evidence for semantics, a live offline tool turn as evidence for integration, and repeated checked tasks as evidence for capability. Report missing SDK, real devices, profile access or benchmarks precisely; continue with useful fixtures or independent work. Never report a feature or platform as passed from a plan, unrun check, or related device.

## Scope decisions during development

Work in coherent milestones and commit reviewable slices. Keep dependencies, event APIs and instructions minimal until a use case requires more. Do not begin with feature parity, dynamic extension execution, generalized shell access, model training, automatic cloud escalation, cross-device sync, or custom accelerator kernels. New proposed features should identify the user workflow, platform permissions, tests and measurable benefit. Proceed with reversible implementation choices without asking routine questions; state assumptions and reopen choices when integration evidence changes them.
